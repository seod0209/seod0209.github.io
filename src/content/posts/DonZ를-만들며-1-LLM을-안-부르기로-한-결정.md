> 생년월일로 어울리는 차를 추천하는 콘텐츠를 만들었다. 얼핏 "LLM 실시간 생성" 각으로 보였는데, 결과 공간을 세어보니 LLM이 필요한 문제가 아니었다. 이건 **AI를 잘 붙인 이야기가 아니라, AI가 필요 없는 문제라는 걸 발견한 이야기**다.

## 처음에는 LLM 문제처럼 보였다

기획은 단순했다. 생년월일시를 받아 사주를 풀고, 거기 어울리는 차를 한 대 추천하고, 왜 그런지 설명 문구를 붙인다. "설명 문구"라는 단어가 나오는 순간 머릿속에 그려진 구조는 이거였다.

```
생년월일시
  ↓
사주 계산
  ↓
LLM  ← 추천 + 설명 문구 생성
  ↓
차량 추천 카드
```

이대로 갔으면 프롬프트를 다듬고, API 키를 숨기고, 레이트리밋을 걸고, 응답 지연을 견디는 흔한 LLM 앱이 됐을 거다. 그 전에 결과가 몇 가지나 나오는지부터 세어봤다.

## 그런데 결과 공간부터 세어봤다

입력은 무수히 많다. 연·월·일·시진·양음력·성별 조합은 수만 가지다. 하지만 추천을 **결정하는 핵심 분류값**은 하나였다 — 사주의 일주(日柱), 즉 **60갑자**.

- 사용자가 뭘 넣든 결과는 60개 일주 중 하나로 떨어진다.
- 차량 데이터도 카탈로그 108종으로 고정돼 있다.
- 그러면 LLM이 실제로 "생성"해야 할 자연어는 사용자 수만큼이 아니라, **일주 60건**이 전부다. 같은 일주면 설명도 같아도 된다.

핵심은 "입력 경우의 수가 적다"가 아니다. 입력은 오히려 많다. 핵심은 **LLM이 생성해야 할 의미 있는 결과 공간이 유한하고 작다**는 것이었다. 60건은 사람이 한 번 만들어두면 끝나는 양이다.

## 생성 문제가 아니라 조회 문제였다

결과 공간이 60이라는 걸 인정하자 구조가 뒤집혔다.

```
생년월일시
  ↓
60갑자 분류        ← 계산으로 확정
  ↓
미리 계산한 후보군  ← 일주별 후보 6대(실구매 5 + 히든 1)
  ↓
deterministic selection  ← 후보 중 1대 확정
```

각 일주별 후보군을 미리 계산해 JSON으로 박아두면, 런타임에 자연어를 생성할 이유가 없다. 문구 톤을 바꾸고 싶으면 60건을 한 번 다시 뽑아 사람이 훑고 교체하면 된다 — **서비스 운영 중엔 모델을 아예 호출하지 않는다.**

이건 생성(generation) 문제가 아니라 조회(lookup) 문제였다. 그리고 조회 문제엔 LLM이 없다.

## LLM을 지우자 같이 사라진 것들

런타임에서 모델을 걷어내니, 모델과 함께 딸려오던 걱정거리들이 통째로 사라졌다.

- **LLM 토큰 비용: 0** — 봇이 10만 번을 돌려도 LLM 비용은 0원이다. (CDN·함수 호출 같은 인프라 비용은 별개지만, 그건 정적 콘텐츠 서빙 수준이다.)
- **LLM API Key 관리: 불필요** — 키가 존재하지 않으니 유출될 키도 없다.
- **LLM Prompt Injection 공격면: 소멸** — 사용자 입력을 넘길 모델 자체가 없다. 웹 전반의 인젝션이 사라진다는 뜻이 아니라, *LLM 프롬프트 인젝션이라는 공격면 하나가 아예 없어졌다*는 뜻이다.
- **LLM latency: 없음** — 결과는 JSON 조회 속도로 즉시 뜬다.
- **LLM rate limiting: 불필요** — 비용이 트래픽에 비례하지 않으니 요청을 막을 이유가 없다.

## 개인정보도 서버로 보낼 이유가 없어졌다

조회 구조의 부수 효과가 하나 더 있었다. 추천 기능에서는 **생년월일시 → 일주 계산을 브라우저에서** 수행하고, 원본 입력을 서버로 보내지 않는다. 추천 한 대를 얻기 위해 생년월일시를 **서버에 저장·전송해야 하는 문제가 사라진** 것이다.

공유 링크도 이 약속을 지킨다. 결과 카드는 일주 인덱스와 차량 인덱스만 있으면 복원되므로, 공유 URL엔 그 두 숫자만 담고 생년월일·성별은 싣지 않는다.

```ts
// share.ts
// 결과 카드는 60갑자 인덱스와 추천 차량 인덱스만 있으면 그대로 복원되므로,
// 생년월일·성별 같은 입력값은 링크에 담지 않는다.
```

과장하진 말자. 사이트 전체로 보면 방문 분석(GA)을 쓰고, 오행 궁합 같은 다른 기능은 서버 계산(BFF)을 거친다. 그래서 "개인정보처리방침 이슈가 소멸했다"고 말하면 거짓이다. 정확히는 **이 추천 기능에 한해, 민감한 원본 입력을 서버로 넘길 이유가 없어졌다**는 것이다. 범위를 좁혀 말하는 게 맞다.

## 같은 입력은 같은 결과

후보 6대 중 최종 한 대는 랜덤이 아니라 **결정적 시드**로 고른다. 같은 사람은 언제 눌러도 같은 차를 받아야 콘텐츠로서 말이 된다.

```ts
// recommend.ts — FNV-1a 32bit 해시 % n
export function seedPick(key: string, n: number): number {
  let h = 2166136261;
  for (let i = 0; i < key.length; i++) {
    h ^= key.charCodeAt(i);
    h = Math.imul(h, 16777619) >>> 0;
  }
  return h % n;
}
```

시드 키는 입력을 이어붙인 문자열이다.

```ts
// ilju-widget.tsx
const item = ILJU_RESULTS[info.index];              // 일주로 후보군 확정
const key  = [year, month, day, mode, si, sex].join('|');
const pick = seedPick(key, item.cars.length);       // 후보 중 1대
```

여기서 성별(`sex`)이 시드에 들어간다. 그런데 이게 **성별로 차종을 가르는 것과는 다르다.** 후보군 `item.cars`는 일주 인덱스만으로 정해지고 남녀가 동일하다. 성별은 그 6대 중 몇 번째를 집을지에만 섞인다.

```
나쁜 설계                         현재 설계
성별                              일주
 ↓                                ↓
남성 차량군 / 여성 차량군          동일한 후보군 (성별 무관)
 ↓                                ↓
추천                              성별 포함 시드 → 후보 중 1대 선택
```

"여성이면 경차, 남성이면 스포츠카" 같은 고정관념을 콘텐츠에 넣지 않으려는 의도적 설계다. 그러면 질문이 남는다 — **후보를 안 가를 거면 성별을 아예 입력에서 빼지, 왜 시드엔 남겼나?** 남긴 이유는 하나다. 생년월일시가 완전히 같은 두 사람이 항상 문자 그대로 똑같은 한 대를 받는 것보다, 성별 한 비트로 갈라주는 편이 콘텐츠로서 덜 심심하기 때문이다. 콘텐츠엔 안 쓰고 선택 다양성에만 쓰는 것 — 입력 폼도 성별 힌트를 "추첨 시드에 반영"이라고 정직하게 적어둔다. (없어도 서비스가 성립한다는 점에서, 이건 재검토 여지가 있는 선택이기도 하다.)

## 그렇다고 클라이언트가 안전한 건 아니다

위젯엔 호출 스로틀이 있다. 1.5초 쿨다운, 분당 12회.

```ts
// recommend.ts
export function makeThrottle(cooldownMs = 1500, maxPerMin = 12): () => string | null {
  let hist: number[] = [];
  return () => {
    const now = Date.now();
    hist = hist.filter((t) => now - t < 60000);
    if (hist.length && now - hist[hist.length - 1] < cooldownMs) return '잠시 후 다시 시도해주세요.';
    if (hist.length >= maxPerMin) return '요청이 너무 잦습니다. 1분 후 다시 시도해주세요.';
    hist.push(now);
    return null;
  };
}
```

분명히 해두자. 이건 세션 안에서만 사는 클로저라, 개발자도구로 얼마든지 우회된다. **서버를 지키는 보안 장치가 아니라, 실수로 연타하는 걸 막는 UX 제약**이다. 개발 글에서 `if (tooManyRequests) return;`을 만들어 놓고 레이트리밋이라 부르는 걸 종종 보는데, 브라우저 코드는 방어선이 아니다. 다행히 지금 구조에선 우회당해도 잃을 게 없다(LLM을 안 부르니까). 그래서 이 정도로 충분하다.

> 외부 API가 필요한 기능이 생기면 얘기가 달라진다. 그때를 대비한 방어형 프록시도 만들어뒀지만, 현재 추천 경로에서는 쓰지 않는다. 그건 별도 글로 다룬다.

## 내가 얻은 결론

AI를 얼마나 잘 붙일지 고민하기 전에, **이 문제가 정말 생성 문제인지부터 세어봤어야 했다.** 결과 공간이 60이라는 걸 확인한 순간 LLM·API 키·인젝션·레이트리밋·서버 저장이 한꺼번에 사라졌다. 가장 좋은 최적화는 부를 필요가 없는 걸 안 부르는 거였다.

## 관련 작업

- 추천 경로: `src/lib/ilju/engine.ts`(생년월일시 → 60갑자, 클라이언트 계산) → `src/lib/ilju/data.ts`(사전생성 `ilju_car_60.json` 조회) → `src/lib/ilju/recommend.ts`(`seedPick` FNV-1a 결정적 선택, `makeThrottle` UX 스로틀).
- 시드 조립·제출: `src/app/saju-car/_components/ilju-widget.tsx` (`[year, month, day, mode, si, sex]`).
- 공유 링크가 원본 입력을 안 담는 근거: `src/lib/ilju/share.ts`.
- 문구 재생성 파이프라인(운영 중 비호출): `ilju-widget/PROMPT.md`, `build_data.py`.
- 다음 편: 「생년월일 하나가 생각보다 어려웠다 — 음력·야자시·진태양시」에서 위 "클라이언트에서 60갑자 계산" 한 줄의 실제 난이도를 다룬다.
