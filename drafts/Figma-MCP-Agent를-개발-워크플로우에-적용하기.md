Figma MCP와 agent를 "질문 답변기"처럼 쓰면 금방 한계가 온다. Figma URL만 던지고 "이대로 구현해줘"라고 하면, 에이전트가 어떤 프레임을 기준으로 읽었는지, mobile/tablet/desktop 중 무엇을 source of truth로 삼았는지, 토큰과 raw value를 어떻게 구분했는지 검수하기 어렵다. 이 글은 Figma MCP 기반 agent 작업에서 **입력 기준·breakpoint 계약·티켓 전달 방식**을 어떻게 잡아야 하는지 정리한 초안이다.

> 검증 범위: 이 글은 현재 사내 티켓/agent 실행 로그를 대조한 회고가 아니라, Figma MCP agent 작업에 넣을 운영 기준을 정리한 초안이다. 로컬 Astro 렌더링은 검증했지만, 실제 사례 인용처럼 읽히는 문장은 의도적으로 기준형 문장으로 낮춘다.

## 원칙: "물어보기"에서 "끼워 넣기"로

채팅으로 물어보는 것과 파이프라인 단계로 붙이는 것의 차이는 이렇다.

- **물어보기**: 사람이 매번 맥락을 복붙해서 넣는다. 결과 품질이 그날 프롬프트에 좌우된다.
- **끼워 넣기**: 입력이 항상 같은 형식으로 들어오고, 출력도 정해진 형식으로 나온다. 재현 가능하고, 검수 지점이 명확하다.

핵심은 **입력과 출력을 형식화**하는 것이다. "이 diff를 리뷰해줘"가 아니라 "이 diff에서 (1) 잠재 버그 (2) 네이밍 (3) 누락된 예외처리를 각각 항목으로 뽑아줘"처럼, 출력 스키마를 먼저 정한다. 그래야 결과를 사람이 훑고 취사선택하기 쉽다.

## 1. 코드리뷰 보조

리뷰를 대체하려는 게 아니라, **사람이 보기 전에 1차 필터**를 돌리는 용도다. 커밋이나 PR의 diff를 넣고 정해진 관점 몇 가지로만 훑게 한다.

붙이는 방식은 단순하다. diff를 뽑아서 프롬프트에 넣고, 관점을 고정한다.

```bash
# 예: 최근 커밋 diff를 리뷰 프롬프트로 넘기기
git show --no-color HEAD | your-llm-cli --system "$(cat review-prompt.txt)"
```

`review-prompt.txt`에 관점을 못 박아둔다.

```
너는 코드리뷰 보조다. 아래 diff에서만 근거를 찾아 답한다.
1) 이 변경으로 생길 수 있는 버그/엣지케이스
2) 네이밍/일관성 문제
3) 누락된 예외처리나 방어코드
확실하지 않으면 "확실치 않음"이라고 적어라. diff 밖의 코드를 추측하지 마라.
```

내가 얻은 것과 주의점:

- **얻은 것**: 사람 리뷰어가 놓치기 쉬운 "null 안 봤네", "여기 await 빠졌네" 같은 기계적인 지적을 미리 걸러준다. 리뷰어는 설계·의도 같은 진짜 판단에 집중할 수 있다.
- **주의점**: LLM은 diff 밖 맥락을 모른다. "이 함수 호출부가 잘못됐다"류 지적은 diff에 호출부가 없으면 상상해서 답하기 쉽다. 그래서 프롬프트에 "diff 밖을 추측하지 마라"를 반드시 넣는다. 최종 판단은 사람이 한다.

## 2. 문서화

가장 실용적이었던 영역. 문서는 "쓰긴 써야 하는데 손이 안 가는" 대표적인 작업이라 초안 생성에 LLM이 잘 맞는다.

- **커밋 메시지 → 릴리스 노트 초안**: 한 스프린트치 커밋 제목을 모아 넣고 "사용자 관점 변경사항만 카테고리별로 묶어달라"고 시킨다. 완성본이 아니라 초안이다. 다듬는 건 사람이 한다.
- **코드 → 설명 초안**: 복잡한 함수 하나를 넣고 "무엇을 하는지, 입력·출력·예외를 표로" 뽑게 한다. 주석/문서 초안으로 쓴다.
- **의사결정 기록(ADR) 초안**: "왜 A 대신 B를 골랐나"를 대화로 정리한 뒤 정해진 틀로 요약하게 한다.

여기서도 원칙은 같다. **완성본을 기대하지 않는다. 초안을 받아서 사람이 완성한다.** LLM이 만든 문서를 검수 없이 올리면, 그럴듯한데 미묘하게 틀린 문장이 섞여 들어간다.

## 3. 적용 기준: 모바일 디자인에서 태블릿·데스크톱까지 넓히기

처음 mobile 시안만 전달되고, 나중에 tablet / desktop 시안이 추가되는 상황은 Figma MCP agent가 특히 흔들리기 쉽다. 그냥 "반응형으로 맞춰줘"라고 던지면 mobile 기준 구조를 유지해야 하는지, tablet부터 레이아웃이 바뀌는지, desktop에서 정보 밀도가 늘어나는지 같은 판단이 프롬프트 밖으로 빠진다.

그래서 작업 기준은 이렇게 잡는다.

1. **mobile을 기준 구현으로 고정한다.** 먼저 mobile 시안만 보고 컴포넌트 구조·데이터 흐름·토큰 사용을 잡는다. 이 단계에서는 tablet/desktop을 상상해서 미리 추상화하지 않는다.
2. **tablet/desktop이 추가되면 "새 구현"이 아니라 "차이 목록"으로 본다.** breakpoint, grid column 수, max-width, padding, 노출/숨김 정보, CTA 위치처럼 mobile 대비 달라지는 값만 표로 뽑는다.
3. **에이전트 지시문을 viewport matrix 형태로 바꾼다.** "반응형 처리" 대신 `mobile / tablet / desktop` 별 기대 레이아웃, 유지해야 할 공통 컴포넌트, 바뀌어도 되는 스타일 축을 명시한다.
4. **티켓도 화면 단위가 아니라 breakpoint 계약 단위로 쪼갠다.** 예를 들어 "상담신청 카드 반응형"이 아니라 "상담신청 카드: 360 / 768 / 1440 viewport에서 CTA 위치와 카드 max-width 정합"처럼 검수 가능한 조건으로 적는다.

agent 지시문은 이런 형태로 고정한다.

```text
목표: 기존 mobile 구현을 유지하면서 tablet/desktop 시안을 추가 반영한다.

고정 계약:
- mobile 360px 레이아웃은 회귀시키지 않는다.
- 컴포넌트 분리는 유지한다. viewport별 파일 복붙 금지.
- 색/간격/타이포는 디자인 토큰만 사용한다.

viewport matrix:
- mobile: 1 column, full-width CTA, horizontal padding 20
- tablet: 2 column 가능, content max-width 지정, CTA는 카드 하단 유지
- desktop: centered container, max-width 1200, CTA는 우측 summary 영역 고정

출력:
- 수정 파일 목록
- viewport별 변경 요약
- 확인한 화면 폭과 남은 불확실성
```

Figma URL을 넘길 때도 읽기 기준을 따로 둔다. 에이전트가 파일 전체를 훑거나, 현재 선택된 프레임 하나만 보고 나머지를 상상하면 안 되기 때문이다.

```text
Figma 읽기 기준:
- URL은 반드시 구현 대상 frame/node 기준으로 전달한다. 파일 루트 URL만 던지지 않는다.
- mobile / tablet / desktop 프레임이 따로 있으면 세 URL 또는 node id를 모두 전달한다.
- 먼저 frame hierarchy를 읽고, 그다음 스타일 값을 읽는다. 보이는 픽셀보다 구조가 우선이다.
- component instance면 원본 컴포넌트명과 override된 값만 구분해서 기록한다.
- auto layout, constraints, grid, max-width, padding, gap, hidden layer를 breakpoint별로 비교한다.
- 색/폰트/간격은 raw value를 그대로 하드코딩하지 말고 token 매핑 가능성을 먼저 확인한다.
- 이미지·아이콘·카피처럼 구현에 필요한 asset은 누락 여부를 별도 목록으로 남긴다.
- 읽지 못한 값은 추측하지 말고 "확인 필요"로 남긴다.
```

이 기준을 넣은 이유는 단순했다. Figma URL 하나에는 너무 많은 정보가 들어 있고, 에이전트는 읽는 범위를 잘못 잡으면 그럴듯한데 틀린 결론을 낸다. 그래서 "어디를 읽을지"와 "무엇을 우선 비교할지"를 분리했다. URL은 대상 노드를 좁히는 입력이고, agent 지시문은 그 노드에서 구조·토큰·breakpoint 차이를 어떤 순서로 뽑을지 정하는 계약이 됐다.

핵심은 에이전트에게 "예쁘게 반응형으로"를 시키지 않는 것이다. 대신 **무엇이 유지돼야 하고, 무엇만 viewport별로 달라지는지**를 계약으로 준다. 그러면 에이전트는 추측해서 새 화면을 만드는 쪽이 아니라, mobile 기준 구현 위에 tablet/desktop 차이를 얹는 쪽으로 움직인다.

티켓에도 같은 구조를 넣어야 한다. 본문은 길어져도 괜찮으니 다음 네 가지를 반드시 적는다.

- **기준 시안**: mobile이 source of truth인지, desktop이 최종 기준인지.
- **breakpoint별 차이**: 레이아웃·간격·노출 정보·CTA 위치.
- **회귀 금지 조건**: 이미 QA된 mobile 동작, 접근성, 데이터 바인딩.
- **검수 방법**: Storybook/로컬 페이지에서 확인할 viewport 폭과 체크리스트.

이 구조를 쓰면 작업이 두 가지로 안정된다. 첫째, tablet/desktop 추가가 "다시 만들기"로 번지지 않는다. 둘째, 리뷰할 때도 "느낌이 다르다"가 아니라 "768px에서 카드 max-width가 티켓과 다르다"처럼 말할 수 있다. LLM을 쓰든 사람에게 넘기든, 반응형 작업은 감각보다 **breakpoint 계약**으로 전달해야 덜 흔들린다.

## 4. 자동화 (반복 변환·정리)

정형화된 텍스트 변환 작업에 붙였다.

- 로그/에러 메시지 → 원인 후보 정리
- 정해진 포맷 간 변환(예: 표 → 마크다운, JSON 키 이름 규칙 통일 제안)
- 반복적인 보일러플레이트 초안 생성

이 영역의 함정은 **결정론이 필요한 곳에 LLM을 쓰는 것**이다. "매번 정확히 같은 결과"가 필요한 변환은 스크립트로 짜야지 LLM에 맡기면 안 된다. LLM은 "규칙을 아직 못 정한", "매번 조금씩 다른" 반정형 입력을 다룰 때 값을 한다. 규칙이 굳으면 그때 코드로 내린다.

## 붙일 때 지켰던 규칙 3가지

1. **입력·출력 형식을 먼저 정한다.** 자유서술 대신 스키마. 그래야 검수·자동화가 된다.
2. **근거 범위를 프롬프트에 못 박는다.** "주어진 것 밖을 추측하지 마라." 환각을 줄이는 가장 싼 방법이다.
3. **결과는 항상 사람이 게이트한다.** LLM 출력은 초안이지 커밋이 아니다. 검수 지점을 워크플로우에 명시적으로 남긴다.

## 정리

Figma MCP Agent를 워크플로우에 붙여서 얻고 싶은 건 "빨라졌다"보다 "귀찮아서 안 하던 기준 정리를 하게 됐다"에 가깝다. 리뷰 1차 필터, 문서 초안, 반정형 변환, 그리고 Figma 기반 반응형 디자인 차이 정리 — 넷 다 사람이 하기엔 지루하고 미루기 쉬운 일이다. agent를 그 자리에 끼워 넣되, 입력 형식을 정하고, 읽을 범위를 제한하고, 최종 판단은 사람이 쥔다. 이 세 가지만 지키면 대체로 손해 보지 않는다.
